# 江湖录 Demo · B 版「竖向长卷」设计（atlas）

## 1. 背景

A 版「古风地图打卡册」已完成并上线（`https://game.joho.cn/jianghu1/`），表现层是**一屏可览**的竖幅画卷 `views/album/`。

本设计是规划中的 B 版：`views/atlas/`。命题是「**地图溢出屏幕、靠拖拽与缩放去探索**」，用来和 A 版的「册页感」做对比，判断江湖录该走清单式还是空间式。

## 2. 目标与非目标

### 目标

- 地图为**竖向长卷**，初始取景在旅程起点（画卷下缘），靠纵向拖拽向山巅推进，内容纵深约 1.7 屏
- **雾分两层**：未到达路段整块雾（门槛驱动）+ 段内未解锁点位径向雾
- **留痕分两层**：脚印点序列 + 已走过路段转实墨线
- **缩放**：可退到纵览全卷，也可放大到 1.6 倍；`s ≤ 1` 时纯纵向，`s > 1` 时解锁横向拖
- `shared/` 与 `platform/` **零改动**，全部差异落在 `views/atlas/`

### 非目标（本次明确不做）

- **不做探索驱动的雾**（视口扫过即擦亮）。那需要记录「已探索区域」并塞进存档，是 B 版最贵的一条；本轮先用门槛驱动的雾验证「拖拽本身」的价值
- **不做导航辅助**：不加右缘刻度尺、不加「寻」按钮。理由：a) 雾与墨线已充分引导；b) 加按钮会让「拖拽探索」这个核心动作变成可选，把结论洗掉；c) §4.3 的「退到纵览全卷」本身就是免费的纵览手段，正好补上这个缺口
- **不做惯性滑动、不做双击复位**。先验证基本手感，手感确实差再加
- **不改动 A 版**任何视觉与行为（唯一例外是 §3 的互动组件上提，属路径调整）
- 不接正式美术素材、不做小游戏适配

## 4. 几何模型

### 4.1 长卷尺寸与点位重映射

**必须先做重映射，不能简单拉伸画布。** 实测 `content.ts` 里六个点位的归一化 y 落在 **0.22 ~ 0.74**（跨度 0.52），若只是把画布从 1280 拉到 2160，点位跨度只有 `0.52 × 2160 = 1123`，**仍小于一屏 1280** —— 点位会全在一屏内，B 版「溢出屏幕」的前提直接不成立。

因此：

- 长卷画布：**720 × 2880**（上下各留 360 的装饰边）
- 点位重映射：把 `[minY, maxY]` 线性铺满 `[MARGIN, H − MARGIN]`

```ts
const MARGIN = 360;
const H = 2880;
const minY = Math.min(...points.map(p => p.y));   // 动态取，不硬编码 0.22
const maxY = Math.max(...points.map(p => p.y));   // 动态取，不硬编码 0.74
py(y) = MARGIN + ((y - minY) / (maxY - minY)) * (H - 2 * MARGIN);
```

按当前内容层数值：点位 py 落在 **360 ~ 2520**，跨度 **2160 = 1.69 屏** —— 这才是「约 1.7 屏」的来源。`minY`/`maxY` 动态取，日后改内容层坐标不会崩。

### 4.2 视口与平移约束

定义**虚拟视口 = 地图单位下的 720×1280 矩形**，它就是「一屏」。

SVG 固定 `viewBox="0 0 720 1280"`、`preserveAspectRatio="xMidYMid slice"`，实际 CSS 尺寸由布局决定；地图内容包在 `<g transform="translate(tx ty) scale(s)">` 里。`s = 1` 时地图宽 720 正好铺满虚拟视口宽。

视口实际显示的地图区间是 `[−ty, −ty + 1280]`（纵向）、`[−tx, −tx + 720]`（横向）。

约束（`W(s) = 720s`、`H(s) = 2880s`）：

```
clampAxis(view, content):
  if content <= view:  返回 (view - content) / 2      // 居中锁定
  else:                返回 [view - content, 0]        // 可拖区间
```

- **纵向**：`s ≤ 0.4444` 时 `H ≤ 1280` → 居中锁定；否则 `ty ∈ [1280 − 2880s, 0]`
- **横向**：`s ≤ 1` 时 `W ≤ 720` → 居中锁定（横向不可拖）；`s > 1` 时 `tx ∈ [720 − 720s, 0]`

`s = 1` 是横向行为的分界点：**放大的那一刻横向才解锁**。这是有意的——横向自由只在玩家主动凑近后出现。

### 4.3 缩放范围

- `s_min = 0.45`：`H = 1296 ≈ 1280`，整卷退到一屏内可览。此时地图显示宽 324，两侧各露约 198 单位案面。这个「纵览全卷」是 §2 中「不加导航辅助」的补偿手段，因此保留
- `s_max = 1.6`：地图显示宽 1152，横向可拖 **0.6 屏**
- 初始 `s = 1`

### 4.4 初始取景

**初始视口下缘贴合画卷下缘**：`ty = 1280 − 2880 = −1600`，即显示地图 `[1600, 2880]`。

这样段一（松花江渡口一带）尽收眼底，且下方露出 360 装饰边。玩家向上拖 = 向山巅推进。

**注意方向**：内容层里渡口 `y = 0.74`（偏下）、山巅孤松 `y = 0.22`（偏上），因此长卷是**渡口在下、山巅在上**，与「登山」隐喻一致；旅程推进 = **向上拖**，`ty` 从 −1600 增大到 0。此处不翻转 y。

### 4.5 缩放锚点

捏合以双指中点为锚，保持该点在地图上的位置不动：

```
设锚点在虚拟视口坐标 (ax, ay)
m = ((ax - tx) / s, (ay - ty) / s)     // 锚点地图坐标
s' = clamp(s * 缩放比, s_min, s_max)
tx' = clampAxis(ax - m.x * s', ...)    // 再按 §4.2 约束
ty' = clampAxis(ay - m.y * s', ...)
```

## 5. 手势

容器设 `touch-action: none`（`index.html` 已有 `user-scalable=no`，不会与页面缩放打架），用 **Pointer Events** 自行实现：

- 维护 `Map<pointerId, {x, y}>`
- 1 个活动指针 → 平移：`tx += dx`、`ty += dy`，随后 clamp
- 2 个活动指针 → 捏合：以两指中点为锚调用 §4.5
- `pointerdown` 时 `setPointerCapture`，`pointerup/cancel` 时从 Map 移除
- 指针从 2 个减到 1 个时**重新播种**基准点，避免跳变

## 6. 雾（两层）

### 6.1 未到达路段整块雾（门槛驱动）

- 覆盖区间：`[0, fogBottom]`，其中 `fogBottom = max(段二点位的 py) + 180`（由内容层坐标经 §4.1 算出，**不硬编码**）。按当前数值 `fogBottom = 1191 + 180 = 1371`
- 因为旅程自下而上，未知区域在**上方**，所以雾是画布**顶部**整块，底边羽化
- 渲染：主体 rect（`#8d97a1`，opacity 0.62）+ 底边 150 单位高的 linearGradient 羽化带
- 消散：段二解锁时对整块雾的 CSS `opacity` 做 **800ms transition** 到 0。解锁判定**复用 `sectionUnlocked()`**（`rules.ts` 已有），门槛值来自内容层 `sections` 的 `requiresStamps` / `requiresScore`（当前 s2 为 3 / 30）。**不新增任何规则函数**

### 6.2 点位径向雾（点位驱动）

- 段二内每个点位各罩一层 `<circle r="360" fill="url(#fogBlob)">`，`fogBlob` 是径向渐变（中心 0.85 → 边缘 0.1）
- 消散：该点位变为可探索时，`opacity` 与 `r` 一起做 600ms transition（`r` 收缩 + 淡出）
- **保证项是 opacity 过渡**；`r` 过渡是增强项（Chrome/Edge/Safari 16+ 支持 SVG 几何属性的 CSS 过渡），旧 Safari 不支持则退化为仅淡出，视觉仍成立

### 6.3 两层叠加的效果

段二被整块雾压暗，点位圆雾在整块雾上再叠一层 → 段二中心更浓。这个浓度差正好是「那儿有东西」的暗示，是**有意保留**的，不是缺陷。

## 7. 留痕（两层）

### 7.1 实墨线（路段驱动）

- 驿道按「**相邻两枚印章是否都已 `done`**」切段渲染；判定与 A 版不同——A 版是**按段解锁**转实线，B 版是**按两端是否都走过**转实线。这个驱动条件的差异正是 B 版与 A 版的差异点
- 已走过段渲两份：细实线（`#8a765a`，width 18）+ 粗半透明晕染副本（width 30，opacity 0.28）
- 未走过段：虚线（`#c9b79a`，width 13，`stroke-dasharray="26 22"`）

### 7.2 脚印点序列（叠在墨线上）

- 在已走过路段上叠一条 `<path>`，`stroke="#c0392b"`、`opacity 0.5`、`stroke-width 22`、`stroke-linecap="round"`，用 `stroke-dasharray` 的**短 dash** 画成一串圆点
- 间距用手写的抖动序列（如 `"2 58 2 66 2 54 2 62 ..."`，约 8 组循环）避免退化成「一串珠子」——**零坐标数据、纯 SVG**，不需要 `getPointAtLength` 之类的 DOM 测量
- 只在已走过段渲染

## 8. 卡片与落章

### 8.1 点位卡片

- `AtlasCard.vue` 沿用 A 版的底部升起结构与内容顺序：点位名 + 关闭 → `lines[]` 逐行渐显（点击可跳过）→ 互动区 → 答对后收起互动区、播放落章、显示「已录入见闻录 · 见闻值 +N」
- 互动区直接复用 `views/interacts/` 的三个组件
- 已 `done` 点位再次打开：只显示 `lines[]` 与完成态，**不重复给奖励**

### 8.2 落章动画（与 A 版的差异）

A 版落章从卡片顶部**飞向地图上的点位**。B 版**不飞向地图** —— 长卷 + 拖拽会让目标点位可能已被拖出视口，坐标不可靠。

改为：落章从卡片顶部飞向 **HUD 的「行脚印 n/6」印章槽**。实现为 app 根层一个 `position: fixed` 的落章元素，起终点由两个元素的 `getBoundingClientRect()` 算出，纯 CSS transition，约 600ms。

### 8.3 见闻录册

`AtlasPanel.vue` 两页签同 A 版语义：见闻录（网格，未得为灰底虚线 + 「？」）、行脚印（6 个印章位）。独立实现，不与 A 版共用组件。

## 9. 入口

`main.ts` 按 URL 参数选择表现层，不引入 vue-router：

```ts
import { createApp } from "vue";
import AlbumApp from "./views/album/AlbumApp.vue";
import AtlasApp from "./views/atlas/AtlasApp.vue";
import "./style.css";

const useAtlas = new URLSearchParams(location.search).get("v") === "atlas";
createApp(useAtlas ? AtlasApp : AlbumApp).mount("#app");
```

- `https://game.joho.cn/jianghu1/` → A 版（**行为与今天完全一致，零回归风险**）
- `https://game.joho.cn/jianghu1/?v=atlas` → B 版

## 10. 验收方式

1. **回归**：`npm test`（现有 `rules` / `engine` 单测，`shared/` 零改动必须全绿）与 `npm run build`（vue-tsc 无报错）必须通过
2. **几何自证**：断言点位 py 跨度 > 1280（当前应为 2160），否则 §4.1 的重映射失效、「溢出屏幕」前提不成立。这条是**首要断言**
3. **冒烟**：新增 `scripts/smoke-atlas.cjs`，共用现有「**读 DOM 必须显式等待**」约定（`count`/`innerText`/`allInnerTexts` 不自动等待，只有 `click` 等操作类 API 才等待），以 `?v=atlas` 进入，覆盖：
   - 首屏渲染出 HUD 与 6 枚印章；初始 `ty = −1600`
   - 拖拽后 `<g>` 的 `transform` 真的改变，且 `ty` 被 clamp 在 `[−1600, 0]`
   - 缩放到 `s_min` / `s_max` 时被正确夹住；`s ≤ 1` 时 `tx` 恒为居中值
   - 段二整块雾在门槛前后的 `opacity` 变化
   - 已走过路段数随完成度增加；脚印点数随之增加
   - 完整闭环：连做到段二门槛（`requiresStamps` 3 / `requiresScore` 30）→ 段二解锁、雾散、新点位可点 → 做完 6 个 → 行脚印 6/6
   - `console` 无报错
4. **截图自检**：拖拽前后 / 雾散前后 / 留痕前后各截一张，自查视觉与手感（沿用 A 版做法）

## 11. 风险

| 风险 | 应对 |
|---|---|
| **点位不溢出**（最致命）。若重映射失效、点位仍挤在一屏内，B 版与 A 版没有差异，本版白做 | §4.1 的重映射是硬前提，§10 第 2 条把它列为首要断言 |
| 重映射后点位被均匀铺满，可能显得「等距、机械」，失去 A 版那种自然聚散 | 验收截图时专门看这点。必要时把线性映射换成轻度非线性（保留原有的疏密关系），但仍不碰内容层 |
| 退到 `s_min = 0.45` 时地图宽仅 324，两侧各露约 198 单位案面，容易被误当成渲染 bug | 案面色 `#ebe4d6` 与地图底色 `#f7f1e3` 刻意只差一档；验收截图明确检查；必要时给地图加一圈描边当「卷轴边」 |
| 放大后横向只有 0.6 屏，拖到边无反馈 | 先不做回弹；若手感确认差，再补边缘阻尼（属 §2 非目标的追加项） |
| 捏合缩放与系统手势冲突 | 容器 `touch-action: none` + Pointer Events 自行实现；横向可拖只在放大后出现，与侧滑返回冲突面小 |
| SVG 几何属性（`r`）的 CSS 过渡在旧 Safari 不生效 | §6.2 已把它降级为增强项，opacity 过渡是保证项 |
| 为迁就 A/B 两版而过度抽象 | 只上提三个纯表现互动组件；`PointCard` 与地图耦合，B 版自写 `AtlasCard.vue`，不做通用卡片抽象层 |
