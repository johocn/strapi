# 江湖录 Demo · C 版「行脚图」设计（avatar）

## 1. 背景

Demo 的目的是用同一套内容与数据层，把「地图打卡」这件事做成三种不同表现，再横向比较，决定江湖录该走哪条路。

|  | A 版 `views/album/` | B 版 `views/atlas/` | **C 版 `views/avatar/`（本设计）** |
|---|---|---|---|
| 地图 | 一屏 720×1280，不可动 | 长卷 720×2880，手拖 + 手缩放 | 长卷 720×2560，**镜头自动跟随角色** |
| 地图上有什么 | 点位图标 | 点位图标 | **一个会走路的角色** + 点位 |
| 触发方式 | 点图标 → 立刻弹卡 | 点图标 → 立刻弹卡 | 点目标 → **走过去，抵达才弹卡** |
| 沿途反馈 | 无 | 雾两层 + 留痕两层 | 无 |
| 要验的命题 | 册页感、清单式 | 空间感、探索式 | **临场感、角色代入** |

A 版已上线（`https://game.joho.cn/jianghu1/`），B 版已完成。本设计是 A 版 spec §12 预留的第三版，做完三版即可横向比较。

## 2. 目标与非目标

### 目标

- 地图为 720×2560 的竖向长卷（正好 2 屏），**镜头缓动跟随角色**，角色锚定在视口 62% 高度处
- **点哪走哪**：点地面或点位，网格 A* 自动寻路，遇水绕桥、遇山绕行
- **点目标即预约触发**：点 ready 点位 → 走过去 → 踏入半径自动升起卡片；路过其它点位不打断
- 走动中再点即**从当前位置改道**
- 角色是**单色剪影小人**，纯 SVG/CSS 动画（腿摆动 + 起伏 + 左右翻转），不接美术素材
- `shared/` 与 `platform/` **零改动**，A 版与 B 版**零回归**

### 非目标（本次明确不做）

- **不做手动拖拽、不做缩放**。这是 C 版与 B 版的分工：B 版是「手拖地图」，C 版是「人走地图」。加进来会同时污染两版的结论
- **不做沿途反馈**（不点亮驿道、不留脚印）。B 版已经用「雾 + 留痕」占了这条，重复投资会把三版差异洗掉
- **不做自由摇杆操控**、不做八方向与多帧美术，朝向只做左右翻转
- **不做「跳过行走」或瞬移**。走动过程正是本版要验的东西，跳过等于把结论删掉
- **不改内容**：六个点位、文案、判据、规则、门槛全部原样复用。C 版只做表现层投影（取舍见 §4.3）
- 不引入任何寻路/动画库
- 不做微信小游戏适配、不接正式美术素材

## 4. 几何模型

### 4.1 地图与投影

```
MAP_W = 720     MAP_H = 2560
VIEW_W = 720    VIEW_H = 1280
MARGIN_V = 400          // 纵向上下留白
CAM_ANCHOR_RATIO = 0.62 // 角色锚在视口 62% 高度处
```

六个点位的归一化坐标沿用 `content.ts`（不放宽、不新增）：

| 点位 | x | y | px = x×720 | py |
|---|---|---|---|---|
| 渡口告示 | 0.16 | 0.74 | 115.2 | 2160.0 |
| 江滩酒坛 | 0.30 | 0.72 | 216.0 | 2092.3 |
| 老船家 | 0.44 | 0.70 | 316.8 | 2024.6 |
| 龙潭 | 0.56 | 0.54 | 403.2 | 1483.1 |
| 守山僧 | 0.72 | 0.42 | 518.4 | 1076.9 |
| 山巅孤松 | 0.86 | 0.22 | 619.2 | 400.0 |

投影公式（与 B 版同法：线性、保留疏密）：

```
yRange(points) = { minY: 最小 y, maxY: 最大 y }        // 现行内容得 0.22 ~ 0.74
projectX(x) = x × MAP_W
projectY(y, range) = MARGIN_V + ((y − range.minY) ÷ (range.maxY − range.minY)) × (MAP_H − 2 × MARGIN_V)
```

必须重映射的理由与 B 版相同：y 只落在 0.22~0.74，直接乘 2560 的话纵向跨度仅 1331，仅略大于一屏，镜头几乎不用动。重映射后跨度 1760，稳过一屏。

### 4.2 相机只有一个自由度

地图宽 720 = 视口宽 720，横向刚好贴合，**没有横向平移**。取景状态就是一个数 `ty`：

```
ty ∈ [VIEW_H − MAP_H, 0] = [−1280, 0]
camTarget(py) = VIEW_H × CAM_ANCHOR_RATIO − py = 793.6 − py
clampTy(ty) = min(0, max(VIEW_H − MAP_H, ty))
stepCamera(ty, target, dt) = ty + (target − ty) × min(1, CAM_SMOOTH × dt)      // CAM_SMOOTH = 6 / 秒
```

指数平滑系数 6 对应时间常数约 0.17 秒。角色以 170 单位/秒走时，镜头稳态滞后约 28 单位，一帧内不会把角色甩出屏。

各地取景位置（夹取后）：

| 停留点 | camTarget | 夹取后 ty | 相对上一步镜头位移 |
|---|---|---|---|
| 渡口告示 | −1366.4 | −1280（夹住） | — |
| 江滩酒坛 | −1298.7 | −1280（夹住） | 0 |
| 老船家 | −1231.0 | −1231.0 | 49 |
| 龙潭 | −689.5 | −689.5 | 542（42% 屏高） |
| 守山僧 | −283.3 | −283.3 | 406（32% 屏高） |
| 山巅孤松 | 393.6 | 0（夹住） | 283（22% 屏高） |

镜头累计位移 1280 = 整个可平移范围，所以「起点 → 山巅」正好把长卷走完一遍。

### 4.3 已确认的取舍：渡口三步镜头不动，但卡片升起时地图让位

渡口告示 → 江滩酒坛 → 老船家三点的 y 是 0.74 / 0.72 / 0.70，投影后纵向只差 68 单位，且底部两点被 `clampTy` 夹住，**镜头一步都不动**，观感是「人在这片江滩上挪了两下」。

这是内容层点位分布过密被 C 版暴露出来的事实，**照实呈现，不做「最小间距去堆叠」**。理由：去堆叠等于改内容投影，三版将不再是同一套内容对比，而这正是本版最想保住的东西。此条同时记入 §10 风险，并在最终对比结论里与「形态问题」区分开。

**收尾修订（首轮实测后追加）**：上一条「镜头不动」有个当时没算到的连带后果 —— 渡口告示抵达时，相机把角色锚在视口 62%、该点位又被 `clampTy` 夹在下缘 68.75%，而卡片是 `position: fixed; bottom: 0` 的浮层（移动端实测 393 单位高，顶沿落在视口 54%）——**印章与角色必然落在卡片之后**，这一步走完等于白走。经确认后**有意偏离**「不做去堆叠」的原约束，但偏离方式不是去堆叠、也不是动相机或几何常量，而是**让地图让位**：

- `.stage` 的 `padding-bottom` 跟随卡片**实测**高度；因正文是逐行浮现（`line-in`）卡片会长高，用 `ResizeObserver` 持续跟住，而不是进门量一次
- 缓动与卡片升起同用 0.28s，两块动效咬在一起
- 长卷因 `preserveAspectRatio="xMidYMid slice"` 重新取景，角色与抵达点位被推高到卡片之上

这样六点位分布、§4.1 投影表、§4.2 相机表一字未改，「三版同一套内容对比」的前提仍成立；改的只是「卡片打开时地图的可视区」。实测（390×844，渡口告示抵达后）：`padding 393` 与卡片 `offsetHeight 393` 咬合；印章底沿 419、角色底沿 433，均高于卡片顶沿 452 —— 完全露出（修订前：`padding 0`、印章底沿 628，被盖住）。

此修订只落在 `views/avatar/AvatarApp.vue`，A/B 版零改动。

## 5. 地形与寻路

### 5.1 地形数据（单一真源）

`avatar-terrain.ts` 导出两样东西，**同一份数据既用来画地物、又用来栅格化成可走网格**：

```ts
export type TerrainKind = "water" | "hill";
export type Poly = { id: string; kind: TerrainKind; points: [number, number][] };
export const TERRAIN: Poly[]           // 2 条水道 + 4 块山体林地
export const BRIDGES: { id: string; x: number; y: number; w: number; h: number }[]  // 桥 / 石磴
```

具体坐标（地图单位，`y` 向下）：

- **江**（water，横贯分割）：上缘 `(0,1720)(140,1700)(300,1690)(460,1712)(720,1700)`，下缘反向 `(720,1826)(460,1838)(300,1810)(140,1820)(0,1840)`
- **溪**（water，横贯分割）：上缘 `(0,1262)(180,1240)(380,1252)(560,1236)(720,1250)`，下缘反向 `(720,1310)(560,1296)(380,1312)(180,1300)(0,1322)`
- **山体一**（hill）：`(60,1760)(170,1700)(230,1800)(150,1880)(70,1850)` —— 江左侧，把左岸的死路堵上，逼 A* 走桥
- **山体二**（hill）：`(155,1478)(168,1392)(205,1352)(240,1358)(272,1400)(288,1474)(243,1458)(198,1466)` —— 龙潭左侧
- **山体三**（hill）：`(325,828)(338,752)(378,702)(405,712)(442,758)(468,826)(425,812)(372,818)` —— 龙潭与守山僧之间的左侧
- **山体四**（hill）：`(335,366)(348,296)(386,252)(414,262)(450,302)(478,364)(433,352)(382,358)` —— 山巅左下
- **桥**（可走）：`{ x: 280, y: 1660, w: 70, h: 200 }`
- **石磴**（可走）：`{ x: 196, y: 1215, w: 54, h: 120 }`

山体二/三/四原稿是四个顶点的轴对齐矩形，渲染出来是半透明方块，与治愈系国风基调不符；收尾时改为八点山影（有峰有肩、边不平行坐标轴），**新顶点全部落在原包围盒内**，`hill_1`（功能承重：逼 A* 走桥）、两条水道与两处桥面未动。改形后单测仍 27/27，五段驿道总长 2210（原 2209.9），山体二中心仍为障碍格。

约束（写入单测）：

1. 每块多边形与任一点位的最近距离 ≥ 90 单位（六点位与地形不重叠）
2. 除两条水道外，没有任何地形把地图切成孤岛
3. 两条水道各有一处桥面把它们重新连通

### 5.2 栅格化与 A*

```
CELL = 20                       // 网格边长 → 36 × 128 = 4608 格
NAV_RADIUS_CELLS = 4            // 点位周围强制可走的格数（4 × 20 = 80 单位）
ARRIVE_RADIUS = 55              // 抵达判定：剩余路径短于此值即停
WALK_SPEED = 170                // 地图单位 / 秒
```

顺序：**先把地形铺成障碍格 → 再把桥面挖通 → 最后把每个点位半径 4 格强制置为可走**。第三步是防御性的：即使将来有人挪了点位坐标，也不会出现「点位被障碍包住走不进去」。

A* 为八向，对角代价 √2；起终点各自 `snapToWalkable` 吸附到最近可走格。

### 5.3 驿道 = 相邻点位之间的 A* 路径

C 版不另画驿道数据，而是**按 `points` 数组顺序，把相邻两点用 A* 连起来**，拼成整条驿道，同一份路径也就是角色会走的路。

好处有三：一是驿道自然会走桥、绕山，不会出现「驿道横穿江面」的穿帮；二是驿道与「人走的路」完全一致，可信；三是它顺带把可达性验证做掉了——**五段相邻路线只要有解，六点位就连成一条通路**。单测断言：五段均有解，且「老船家 → 龙潭」这段经过桥面矩形。

### 5.4 兜底

- 点到障碍内部 → 起终点各自吸附到最近可走格（不拒绝点击）
- 路径总长小于 `ARRIVE_RADIUS` 时直接视为已抵达，不做「原地挪一下」的移动
- A* 无解（理论上不该发生）→ 角色不动，该点位渲染为灰态并浮出「此路不通」提示，**不静默失败**
- 改道时从**角色当前位置**吸附格起算，再 prepend 当前位置本身，避免路径回跳
- 标签页隐藏再回来 → 单帧 `dt` 上限截断为 50ms，避免角色瞬移出屏

## 6. 角色

- 一个 `<g class="walker">`，位置 = `translate(px, py)`，朝向用 `scaleX(-1)` 翻转
- 剪影共 4 个图元：头（圆）、袍身（梯形）、双腿（两条带圆头的粗线）、一条手臂。墨色 `#3b342c`，与全局墨色一致
- 走路动画为纯 CSS 关键帧：双腿交替 + 整体上下微起伏，周期约 0.5 秒。只在「走动中」挂类名，停下立刻静止（无待机动画）
- 与地图同处一个 `<g transform="translate(0 ty)">`，所以镜头跟随就是改 `ty` 一个数，不需要另设图层
- 位置完全由路径插值决定，**不反向依赖相机**，避免耦合抖动

## 7. 交互

### 7.1 点击语义（C 版全部规则）

| 点击对象 | 行为 |
|---|---|
| 空白地面 | 只走过去；路上经过任何点位都不弹卡、不打断 |
| ready 点位 | 走过去；进入 `ARRIVE_RADIUS` 即升起交互卡片 |
| locked 点位 | 角色不移动，浮出门槛提示（沿用 `unlockHint`） |
| done 点位 | 走过去；抵达升起只读卡片，可重看 |
| 走动中再点 | 从当前位置重新算路、立即改道，不排队 |
| 卡片开启期间 | 不接受新的点击；关闭后才回到待选 |

### 7.2 状态机

```
待选 ──点地面/点位──▶ 算路 ──▶ 走动中 ──抵达半径──▶ 升起卡片 ──答对──▶ 落章 ──▶ 待选
                                   │                        │
                                   └──再点──▶ 算路          └──关闭──▶ 待选
                                     （从当前位置）
```

- 「预约触发」的实现：点击时记下 `pendingPointId`（点空白则为 `null`），只有抵达该点位半径内才开卡
- 角色停在距点位 55 单位处（`ARRIVE_RADIUS`），视觉上是「站在点位旁边」而不是压在点位图标上
- 关闭卡片不加分、不落章，直接回待选；答对才走落章动画

### 7.3 复用与差异

- 卡片内容区、判据、效果全部走 `shared/`，与 A/B 完全一致
- 三个互动盒（choice / compose / order）复用 `views/interacts/*`，零改动
- 落章沿用 B 版的判断：地图会滚动，飞向点位不可靠，因此**从卡片顶部飞向 HUD 的「行脚印 n/6」印章槽**，纯 CSS transition 约 600ms，起终点由两个元素的 `getBoundingClientRect()` 算出
- 见闻录册 `AvatarPanel.vue` 独立实现，DOM 钩子（`.panel` / `.tab` / `.grid` / `.stamp-board`）与 A/B 保持一致，便于冒烟脚本同构复用

## 8. 数据流

```
用户点击 (指针坐标)
   └─▶ 视口坐标换算 → 地图坐标
        └─▶ snapToWalkable → astar → path
             └─▶ useWalker：rAF 每帧
                    ├─ 沿路径推进 dist += WALK_SPEED × dt → 角色 (px, py) + 朝向
                    ├─ camTarget(py) → stepCamera → ty
                    └─ 剩余距离 < ARRIVE_RADIUS → 停 + 触发 pendingPointId
                          └─▶ pointState(point, state, section) 判定卡片形态
                                └─▶ 卡片提交 → checkAnswer / applyEffects → 落章动画 → persist
```

`avatar-geometry.ts` 里没有 Vue、没有 DOM、没有计时器，只有纯函数；`useWalker.ts` 只负责把纯函数串成时序。

## 9. 入口与三版共存

## 10. 风险

| 风险 | 应对 |
|---|---|
| 走动时长偏短，镜头跟随的存在感集中在后半程（§4.3） | 步速 170 单位/秒 已按 0.7~4.0 秒校准；照实呈现并在对比结论里与「形态问题」区分开 |
| 渡口三步镜头不动，抵达时角色与印章被卡片浮层盖住（§4.3 收尾修订） | 不去堆叠、不动相机与几何常量：`.stage` 的 `padding-bottom` 跟住卡片实测高度，长卷 `slice` 重新取景把角色顶到卡片之上 |
| 栅格化 + A* 是本版唯一有算法风险的模块 | 全部写成纯函数并单测；地形刻意只做两处分割且有桥面连通；单测断言五段相邻路线均有解、且过桥段确实经过桥面 |
| 镜头与角色同帧驱动容易抖动 | 相机指数平滑、角色位置直接由路径插值决定（不反向依赖相机），解算函数均有单测 |
| 三版并存互相污染 | 差异全部落在 `views/avatar/`；`shared/`、`platform/`、`album/`、`atlas/` 零改动；三套冒烟（A/B/C）都必须绿 |
| 「沿途不加反馈」可能让走动变成干等 | 这正是本版要验的命题之一，如实记录；若结论确是等待感明显，再考虑提速或最小反馈 |
| 点位与地形重叠导致不可达 | 栅格化第三步对点位半径 4 格强制可走；地形坐标已按「与任一点位距离 ≥ 90」选定，并由单测守住 |
