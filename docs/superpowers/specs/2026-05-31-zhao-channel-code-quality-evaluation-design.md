# zhao-channel 代码质量评估设计

## 目标

对 zhao-channel 插件进行全面代码质量体检，聚焦"安全可用、稳定可靠、解耦"三个核心目标，产出结构化评估报告和改进路线图。

## 范围

仅 `e:\code\plugins\zhao-channel`，包含 `server/src` 和 `tests`，不涉及其他插件。

## 评估方案：分层扫描法

按安全性 → 稳定性 → 解耦度 → 可维护性四个维度分层扫描，每层用具体指标量化。

### 维度 1：安全性（Security）

| 指标 | 扫描方式 | 风险等级定义 |
|------|---------|------------|
| SQL 注入风险 | 检查 `db.query()` 是否有用户输入直接拼接 | 高：用户输入直接拼接；低：参数化查询 |
| 输入校验覆盖率 | 检查 controller/service 入参是否有 validate/joi/zod | 高：无校验；中：部分校验；低：完整校验 |
| 权限策略覆盖 | 路由 vs 策略的 1:1 对应关系 | 高：路由无策略；低：全部覆盖 |
| 敏感信息泄露 | 日志中是否输出用户 ID/邮箱/密码等 | 高：密码/token；中：用户 ID；低：无 |

### 维度 2：稳定性（Reliability）

| 指标 | 扫描方式 | 风险等级定义 |
|------|---------|------------|
| 错误处理覆盖率 | service 函数中 try-catch / 抛出明确错误 的比例 | 低：>80%；中：50-80%；高：<50% |
| 外部依赖降级 | Redis/DB 不可用时的优雅降级 | 高：未降级直接崩溃；低：降级后功能受限但可用 |
| 边界条件处理 | 空数组/空值/超长输入/并发场景 | 高：未处理；低：已处理 |
| 测试质量 | 集成测试覆盖 + 边界用例比例 | 低：核心路径全覆盖；高：仅 happy path |

### 维度 3：解耦度（Decoupling）

| 指标 | 扫描方式 | 风险等级定义 |
|------|---------|------------|
| 插件间硬依赖 | `strapi.plugin("zhao-*")` 调用次数和位置 | 高：核心路径强依赖；低：可选依赖+降级 |
| `any` 类型密度 | `as any / : any` 数量 / 总代码行数 | 高：>5%；中：2-5%；低：<2% |
| 模块职责边界 | 单文件行数、函数职责是否单一 | 高：>500 行或职责混杂；低：<300 行且职责清晰 |
| 循环依赖 | 模块间 import 关系图 | 高：存在循环；低：无循环 |

### 维度 4：可维护性（Maintainability）

| 指标 | 扫描方式 | 基线定义 |
|------|---------|---------|
| 文件行数分布 | wc -l | >500 行需关注，>800 行需拆分 |
| 函数行数分布 | 逐函数统计 | >50 行需关注，>100 行需拆分 |
| 圈复杂度 | 分支/循环/条件计数 | >10 需简化 |
| 重复代码 | 相似代码段检测 | >20 行相似需提取 |

## 执行方式

每个维度的扫描分三步：

1. **自动扫描** — 用 grep/代码搜索工具批量采集指标数据
2. **人工审查** — 对高风险项逐个阅读上下文，确认是否为真实问题
3. **问题定级** — 按严重程度分为 P0（必须修）/ P1（应该修）/ P2（建议修）

## 交付结构

评估报告文档包含以下章节：

1. **概览** — 评估范围与目标、指标总览表（4 维度 × N 指标，红/黄/绿标记）
2. **安全性评估** — 指标数据、问题清单（P0/P1/P2）、典型问题示例
3. **稳定性评估** — 指标数据、问题清单、典型问题示例
4. **解耦度评估** — 指标数据、问题清单、依赖关系图
5. **可维护性评估** — 指标数据、问题清单、文件/函数热力图
6. **改进路线图** — P0 立即修复（1-3 天）、P1 短期改进（1-2 周）、P2 长期优化（1 月+），每项包含问题描述、修复方案、影响范围

## 约束

- 不做代码修改，只产出评估报告和改进建议
- 每个问题附具体文件路径和行号，可直接定位
- 改进路线图按 P0→P1→P2 排序，P0 项不超过 5 个，确保聚焦
