# 到场核销票据防伪造设计（zhao-point × shao × web）

> 日期：2026-09-25
> 范围约束：**只解决到场核销凭证的可伪造问题**，并给工作人员手动核销补上审计。不改报名/签到业务规则、不动统计口径、不引入 cron。
> 与既有设计的关系：与 [2026-09-25-活动模块缺陷修复-design.md](./2026-09-25-活动模块缺陷修复-design.md) 的 14 项**完全不重叠**（那份覆盖权限树、积分规则键、前端可达性等），可独立交付。

## 1. 问题与证据

当前「到场二维码」是**客户端本地拼的明文串**，不含签名与时效：

- C 端生成：`activity:{活动ID}:{用户ID}`，纯前端 canvas 绘制 — [detail.vue](file:///e:/code/shao/pages/activity/detail.vue#L1652-L1690)
- 工作人员端扫码解析同一明文格式 — [scan.vue](file:///e:/code/web/src/pages/activity/scan.vue#L10-L18)
- 后端直接采信请求体里的 `userId`，不做任何凭证校验 — [controllers/activity.ts:691-702](file:///e:/code/basic/plugins/zhao-point/server/src/controllers/activity.ts#L691-L702) → `activitySvc().checkin({ userId, activityId, method: "worker_scan" })`

**后果**：任何人可自行生成 `activity:{任意活动ID}:{任意用户ID}` 二维码，或直接构造请求，替他人/自己刷到场签到。签到会发积分（[activity.ts:1773](file:///e:/code/basic/plugins/zhao-point/server/src/services/activity.ts#L1773) `grantPoints(...,"activity_attend",...)`）并解锁专属学习包课时（[activity.ts:1776-1778](file:///e:/code/basic/plugins/zhao-point/server/src/services/activity.ts#L1776-L1778)），因此这是**可被外部利用的业务漏洞**，而非单纯体验问题。

附带缺陷：`checkin()` 不校验活动状态（[activity.ts:1742-1752](file:///e:/code/basic/plugins/zhao-point/server/src/services/activity.ts#L1742-L1752)），「仅进行中可签到」只是前端限制（[detail.vue:1432](file:///e:/code/shao/pages/activity/detail.vue#L1432)），后端允许对 `draft/ended/archived` 活动签到。

## 2. 目标与非目标

**目标**

1. 到场凭证改为**服务端签发的随机短时票**，一签一码、一码一用，客户端无法自造。
2. 签发与核销全程留痕（谁、何时、对哪个报名、由哪个工作人员核销），可追溯。
3. 工作人员手动核销（现场无网/用户手机异常时的兜底）保留，但**强制填理由并写审计**。

**非目标**

- 不做票据定时清理任务（沿用现有惰性处理）。
- 不改签到积分规则、地理围栏、报名/候补逻辑。
- 不改 C 端「用户自助签到（self）」路径。
- 不做票据离线校验、不做扫码端扫码后二次确认页。

## 3. 数据模型（方案 B：独立票据表）

新增 content-type `activity-checkin-ticket`（`collectionName: activity_checkin_tickets`），并在 `server/src/content-types/index.ts` 注册。

| 字段 | 类型 | 说明 |
|---|---|---|
| `token` | string，`unique: true`，`private: true` | 24 字节随机 hex，凭证本体 |
| `signup` | relation manyToOne → `plugin::zhao-point.activity-signup`，required | 票据归属的报名记录 |
| `activity` | relation manyToOne → `plugin::zhao-point.activity`，required | 冗余以便跨活动校验与按活动追溯，避免每次 populate 两层 |
| `user` | relation manyToOne → `plugin::users-permissions.user`，required | 持票人，便于按用户查票与审计 |
| `status` | enumeration `["pending","used","expired"]`，default `pending` | 票据生命周期 |
| `expiresAt` | datetime，required | 签发时 = now + 5 分钟 |
| `usedAt` | datetime | 核销时刻 |
| `usedByUserId` | integer | 核销工作人员（up_users.id），审计用 |

**为什么用独立表而不是挂在报名记录上**：一签一码要求同一报名的多次签发各自成记录（刷新、重开页面、异设备），挂在报名上只能存最后一次；且票据表天然是核销流水，可直接用于事后核查与纠纷取证。

**索引/约束**：`token` 唯一索引保证不可碰撞；`signup + status` 用于查「该报名是否已有未过期票」。

**惰性过期**：不引 cron。核销时若命中 `status=pending` 但 `expiresAt < now`，当场置 `expired` 并返回过期错误；签发时若发现该报名存在未过期 `pending` 票，直接复用（避免连点刷库）。

## 4. 接口设计

### 4.1 新增：签发票据（C 端）

```
POST /api/zhao-point/v1/my/activity/:documentId/checkin-ticket   （userRoute 已登录）
→ 200 { token: string, expiresAt: ISO }
```

校验顺序（任一不满足返回 400/403 并给明确文案）：

1. 活动存在（按 `documentId` 查）且 `status ∈ {signup_open, ongoing}`。
2. 当前用户在**该活动**下有 `status = active` 的报名（`waiting` / `cancelled` 拒绝）。
3. 该报名已有未过期 `pending` 票 → 复用并返回原 token；否则新建一条票。

### 4.2 改造：工作人员核销（管理端）

```
POST /api/zhao-point/v1/admin/adm/activities/:documentId/scan-checkin
```

请求体两种形态，二选一：

**A. 扫码核销**（正常路径）

```json
{ "token": "9f3c...a1" }
```

处理：按 `token` 查票 → 校验 `status === "pending"` → 校验 `expiresAt > now`（超出则置 `expired`）→ 校验 `ticket.activity === 当前活动`（防跨活动复用）→ 校验 `ticket.signup.status === "active"` → 调 `checkin({ userId: ticket.user, method: "worker_scan" })` → 成功后票据置 `used` + `usedAt` + `usedByUserId`。

**B. 手动核销**（兜底路径）

```json
{ "userId": 123, "reason": "用户手机没电，出示身份证" }
```

处理：`reason` 必填（trim 后非空，长度 ≥ 2，否则 400「请填写手动核销理由」）→ 调 `checkin({ userId, method: "manual" })` → 在 attendance 上记录 `manualReason` + `operatorId`。

旧格式 `activity:{id}:{userId}` 明文码**一律拒绝**（不是解析失败，而是明确识别后返回「旧版二维码已停用，请让用户刷新页面重新出示」）。

### 4.3 顺带硬化：`checkin()` 补状态校验

在 [activity.ts:1746-1749](file:///e:/code/basic/plugins/zhao-point/server/src/services/activity.ts#L1746-L1749) 找到活动后，增加：`status` 不属于 `signup_open` / `ongoing` 时抛「活动未在进行中，无法签到」。这一条同时保护 self 与 worker_scan 两条路径，且是 4.2 校验的服务端兜底。

**若需缩小改动面，此项可裁剪**，但裁剪后 4.2 的 token 校验将成为唯一防线。

## 5. attendance 表扩展（手动审计）

## 6. 数据流

```
C 端 detail.vue                     后端 zhao-point                      工作人员端 scan.vue
─────────────────                   ──────────────────                   ──────────────────
点「出示到场码」
  └─ POST /my/activity/:id/checkin-ticket
                                   校验活动状态+active 报名
                                   复用或新建 ticket
                                   返回 { token, expiresAt }
  ←─────────────────────────────────
uqrcodejs 渲染 "atk:{token}"
+ 倒计时 + 刷新按钮
                                     ┌──────── 扫码得 "atk:{token}" ←─────┘
                                     │        POST /adm/.../scan-checkin { token }
                                     │      验票（状态/时效/活动/报名）
                                     │      checkin(method=worker_scan)
                                     │      票据 → used
                                     └─ 发签到积分 / 解锁学习包
```

有效期 5 分钟内可反复刷新页面（复用同票）；过期后 C 端点「刷新」重新签发。

## 8. 错误处理与文案

| 场景 | 后端返回 | 前端文案 |
|---|---|---|
| token 不存在 | 400 `invalid_token` | 无效二维码 |
| token 已用过 | 400 `ticket_used` | 该二维码已被核销 |
| token 已过期 | 400 `ticket_expired` | 二维码已过期，请刷新 |
| token 属于其他活动 | 400 `ticket_activity_mismatch` | 二维码不属于本活动 |
| 报名已取消 | 400 `signup_inactive` | 该报名已取消，无法签到 |
| 已签到过 | 200 `{ ok:false, reason:"already_checked_in" }` | 已核销（沿用现有幂等） |
| 手动核销未填理由 | 400 `reason_required` | 请填写手动核销理由 |
| 旧明文码 | 400 `legacy_code_disabled` | 旧版二维码已停用，请让用户刷新页面 |

所有失败路径**均不发放签到积分**（校验全部前置于 `checkin()` 调用）。

## 9. 测试与验收

**自动化（zhao-point `server/tests/`，jest）**

1. 有效票核销成功 → attendance `method=worker_scan`、票据 `status=used`。
2. 过期票 → `ticket_expired`，票据转 `expired`，无积分流水。
3. 跨活动票 → `ticket_activity_mismatch`。
4. `cancelled` 报名持票 → `signup_inactive`。
5. 手动核销缺 `reason` → `reason_required`。
6. 签发接口对 `waiting` 报名 → 拒绝；同一报名 5 分钟内二次签发 → 返回同一 token。

**手工端到端**

1. C 端报名 → 出示二维码 → 工作人员扫码 → 管理端到场名单出现该用户且 `method=worker_scan`；积分流水新增 `activity_attend`。
2. 用旧版明文串自造二维码 → 被拒并提示旧版已停用。
3. 手动输入用户 ID + 理由 → 签到成功且名单可见理由与操作人。
4. 活动结束后持票核销 → 被拒（仅当第 4.3 项保留时适用）。

**部署自检**

- 改的是插件源码 → 必须确认 `Grep dist/server` 命中 `checkin-ticket`、`ticket_expired` 等新关键字，未命中即未重建 dist。

## 10. 影响面与部署

| 仓库 | 改动 | 部署 |
|---|---|---|
| basic（zhao-point） | 新 content-type + 2 处 attendance 字段 + service/controller/routes + dist 重建 | 本地 `npm run build` → commit → `ssh joho` `git fetch && git merge --ff-only origin/main` → `pm2 restart strapi` |
| shao | detail.vue、services/api.ts | `npm run build:h5` + `deploy-h5.ps1` |
| web | scan.vue、api/activity.js | 部署 h.joho.cn |

- **不需要 `npm install`**（无新增依赖），生产不执行 `deploy.sh`，避免 2G 机器 OOM。
- 新表与新增列由 Strapi 启动自动创建，纯新增、不改既有列类型。
- **shao 与 web 必须同批上线**：新码只有新扫码端能识别，旧码已被后端拒绝，任一端先上都会造成一段「扫码核销不可用、只能手动核销」的窗口。请选择非活动时段发布。若确实无法同批，则先上 basic + web（此时任何旧码都会被明确拒绝，现场走「手动核销 + 理由」兜底），shao 紧随其后。

## 11. 风险

1. **现场断网无法出码**：已与用户确认接受（票据需实时签发）。
2. **部署窗口**：两端未同步期间现场核销会失败，需选择非活动时段。
3. **旧页面缓存**：C 端用户停留在旧版页面会出示旧码并失败，需提示刷新；H5 强刷即可恢复。
4. **票据表增长**：每张票一行，量级 = 签到次数 × 刷新次数，当前规模可忽略；清理策略列为挂账。
5. **管理端手动核销仍需人工自律**：加了理由与操作人留痕，属威慑而非技术阻断（用户已确认此取舍）。

## 12. 挂账（明确不在本轮）

- 票据记录清理/归档任务。
- `self` 自助签到的防作弊增强（如设备指纹、反 GPS 模拟）。
- 现场打印名单、批量核销、离线核销模式。
- 与既有设计挂账一致的并发/幂等 4 项（报名占位、并发签到、候补转正重复发奖、台账快照并发）—— 本设计不改这些路径的并发语义。

相关提交：`3b62a66f64`（纯逻辑+单测）、`1840cce23a`（票据表/到场表 schema）、`ee47051910` + `ad24d3fa4a`（服务层签发/核销）、`b29bff99a1`（控制器+路由）、`aa23458f47`（dist）、`9494a53a1a`（TS 类型收窄）、`0c218d7` + `9ef1973`（shao 出码）、`e7cc82b`（web 扫码）、`decf78e021`、`aa6d31737d`（下述两处线上缺陷修复）。

生产实测通过项：未登录签发 → 401；旧明文码 → `legacy_code_disabled`；手动核销缺理由 → `reason_required`；伪造 token / 无凭证 → `invalid_token`；签发票据返回 48 位 hex 且 `expiresAt` ≈ +5min；5 分钟内重复签发复用同一 token；**扫码核销成功**（票据转 `used` 且记 `usedAt`/`usedByUserId`，到场行 `method=worker_scan`、`pointsGranted=true`，积分落 `activity_attend`）；重复核销 → `ticket_used`；过期核销 → `ticket_expired` 且票置 `expired`；过期后重签 → 旧票 `expired` + 新 token；跨活动 → `ticket_activity_mismatch`；活动非进行中 → 「活动未在进行中，无法签到」；手动核销落 `manualReason` 与 `operatorId`。

**本轮上线暴露并修复的两处缺陷（均为「关系字段形状」假设错误，线上 100% 复现）**：

1. `decf78e021` —— `validateTicket` 原先用 `Number(ticket.activity)` 比对活动归属，但 Strapi db 层把 manyToOne 返回为**对象** `{ id }`，`Number({id:7})` = `NaN`，导致**任何有效票据都恒返回 `ticket_activity_mismatch`**，扫码核销全链路不可用。修复：新增 `relId()` 归一 `number | "7" | {id:7}` → `number`，归属比对改用 `relId`；查票补 `populate: { activity: true }`。
2. `aa6d31737d` —— `redeemCheckinTicket` 只 `populate: { signup: true }`，未嵌套 populate `signup.user`，取到的用户 id 为 `undefined` → `NaN` 被透传进 `checkin()` 的 DB 查询，PG 报 `22P02 invalid input syntax for type integer: "NaN"`。修复：`populate: { signup: { populate: { user: true } }, activity: true }`，用户 id 统一走 `relId()`，归一失败时返回业务错误 `invalid_token`（不再泄漏 PG 原始错误）。

**教训**：单测只传了数字形态的 `activity`/`user`，恰好绕过了真实运行时的关系对象形态，两处缺陷都逃过了 9 个单测。凡涉及关系字段取值，必须以 `{ id }` 对象形态入参并补用例。

清理与残留：验收全程在自建临时活动上进行，`zhao` 既有真实活动未被触碰；每轮结束后删除临时活动及其 signup/attendance/ticket/积分记录并 SQL 复核残留为 0。
