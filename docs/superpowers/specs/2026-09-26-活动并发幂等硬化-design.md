## 2. 目标与非目标

**目标**：上述 5 处并发路径下，不变量恒成立：

1. 同一报名至多 1 条 `activity_attendance`，`activity_attend` 积分至多发放 1 次。
2. 同一候补至多被转正 1 次；一次取消至多释放 1 个名额、至多递补 1 人。
3. 同一 (用户, 活动) 至多 1 条 active/waiting 报名。
4. 同一活动快照号不重复。

**非目标**：

- 不改 content-type schema、不做 DDL、不引入 `pg_advisory_lock` / 唯一索引。
- 不做历史脏数据回扫：生产 `activity_signups` / `activity_attendances` 截至 2026-09-26 均为 0 行，无脏数据。
- 不动 `deductPoints` / `refundPoints` 自身的余额快照竞态（见 §7 挂账）。

## 3. 并发不变量与锁序

复用项目已有设施：Strapi 5 `strapi.db.transaction` + 事务 ALS（事务内 `strapi.db.query` 自动绑定同一 trx，见 `@strapi/database` 的 `transactionCtx`）。

两条实现铁律：

- **事务内取 raw knex 必须用回调里的 `trx`**，不能用 `strapi.db.connection`（后者从连接池另取连接，锁与事务无效）。
- 嵌套 `strapi.db.transaction` 复用外层 trx（非 savepoint，内层 `rollback()` 为空操作）——所以内层抛错会冒泡、由外层回滚；若被内层 `catch` 吞掉则事务继续（仅业务错可吞，PG 级错误会让事务进入 aborted 态）。

**全局锁序（防死锁）**：`activities` → `activity_signups` → `up_users`

| 流程 | 锚点锁 | 说明 |
|---|---|---|
| 报名 signup（C4） | `activities` FOR UPDATE | 同时覆盖重复报名复读、名额占位、扣费、落库 |
| 候补转正 promoteWaiting（C2） | `activities` FOR UPDATE | 与报名同锚点，顺位一致 |
| 取消 cancel（C3） | 无（条件更新认领） | 不持锁，靠 `updateMany` 行数决出唯一赢家 |
| 签到 checkin（C1） | `activity_signups` FOR UPDATE | 不触 activities，无逆序 |
| 台账 generate（C5） | `activities` FOR UPDATE | 只锁号段分配与写入，快照读在事务外 |

## 4. 逐项修法

### C1 签到：一次性认领

- 事务内先 `trx("activity_signups").where({id: signup.id}).forUpdate()` 串行化同一报名；
- 事务内**复读** `activity_attendances`（有则返回 `already_checked_in`），再扣到场费、建 attendance、写 `attendedAt`；
- 扣费失败：**直接抛错**让事务回滚（无需补偿 decrement）。
- 积分 `grantPoints` 与学习包授权移到**事务外**补偿执行：失败不阻断已成立的到场记录（保留既有韧性，也避免 PG 级错误污染事务）。

### C2 候补转正：锚点锁 + 复读状态

`promoteWaiting` 拆出 `promoteOneClaim`（事务内，纯认领）：

1. `trx("activities").forUpdate()` 锚点锁；
2. 复读该 signup 状态，非 `waiting` → `stale`（并发者已转正），跳过；
3. 原子占席 `increment`（带容量条件），0 → `no_seat`，结束循环；
4. 收费失败 → 抛错回滚（占席一并归还），外层 catch 记日志后 continue 下一个候选；
5. 条件满足才置 `active`。

积分补发 / 转正通知放事务外，只对 `promoted` 的候选执行。**效果**：两个并发 cancel 拿同一份 pending 列表时，后者在锚点锁后复读到 `active` → stale → 顺延到下一个候选，而不是重复转正同一人。

### C3 取消：条件更新认领

用 `updateMany({where:{id, status:"active"}})` / `({status:"waiting"})` 的**返回行数**判定是否是本次取消的赢家（Strapi 返回 `{count:N}`，必须过 `affectedCount()` 归一，不能 `Number(res)`）。行数为 0 → 并发下后到者，直接 `{ok:true, already:true}` 返回：不通知、不退款、不释放名额、不递补。

保留原语义：仅 `active` 取消才退款（且 `pointsCharged>0`）、释放名额、递补候补；`waiting` 取消只移出队列。

### C4 报名：锚点锁包住「复读 → 占位 → 扣费 → 落库」

把 [activity.ts:765-825](file:///e:/code/basic/plugins/zhao-point/server/src/services/activity.ts#L765-L825) 整段折进一次事务：

锁 `activities` 行 → 复读重复报名（命中 → `dup`）→ 原子占位（0 → 候补分支）→ 档位解析 → 扣费（失败抛错回滚，外层映射为 `insufficient_points`）→ 落库 `active`。

事务外继续原有尾链：`eco-hook`、奖励、分级积分、站内信、企微、试看课时、SOP。**扣费失败不再需要补偿 decrement**——事务回滚已归还占位。

### C5 台账：号段分配加锁

`generate` 的尾段（`prev = count(...)` → `create`）进事务并锁 `activities` 行；`generateAutoIfAbsent` 的「查有无 auto 快照」也进同一把锁，避免 close 自动与手动重归档并发各插一张 auto。

## 5. 新增纯逻辑模块与单测

新增 `server/src/services/activity-concurrency.ts`，只放**可纯函数化**的并发判定，便于单测锁死语义：

- `affectedCount(result)` —— 把 Strapi `updateMany` 的 `{count:N}` / `N` / 异常形状归一为 number（形状坑此前两次引发线上事故）。
- `cancelOutcome({active, waiting})` —— 归一为 `{proceed, notify, refund, releaseSeat, promoteWaitlist}`，直接编码「后到者不得重复释放名额」。

单测 `tests/activity-concurrency.test.ts`：

- `affectedCount` 必须覆盖 `{count:1}` 对象形态、裸数字、`null`/`undefined`/`{}`/`NaN` 回落 0（**关系/返回值形状必须用对象形态入参**，此前两次线上事故都因单测只传数字而漏）。
- `cancelOutcome`：`{active:1}` 全量副作用；`{active:0,waiting:1}` 仅移出队列；`{active:0,waiting:0}` 完全无副作用（并发后到者）。

## 7. 风险与取舍

- **锁粒度**：报名/递补/台账都锚在 `activities` 行，同一活动的高并发报名会串行。活动报名是低频人工操作，可接受；收益是彻底消除超卖与重复行。
- **事务时长**：扣费（嵌套 `deductPoints`）在事务内，事务跨度含 1 次积分写，毫秒级。通知/微信 HTTP 一律留在事务外，不持锁跨网络。
- **行为差异**：C4 扣费失败的错误映射由「吞掉一切」改为「业务错 → `insufficient_points`；其它错误记 warn 后仍按 `insufficient_points` 返回」，与现状一致，仅多一条日志。
- **不加唯一索引**：理论上仍可由绕过 service 的直写造成重复行；本项目所有写入都走 service，接受该残余风险，换取生产零 DDL。
  - 挂账（已全部关闭）：~~`activity_attendances` 无 DB 级唯一约束~~ → 见 §8.2，已用幂等 DDL 补建单列唯一索引。
  - **已补做（同日跟进）**：`deductPoints` / `refundPoints` 加了 `up_users` 行锁 + 事务串行化，与 `earnPoints` 共用同一把锁，消除余额 `balance` 快照列竞态（权威余额本就以 `SUM` 为准）。锁序仍为 `activities → activity_signups → up_users`，无逆序。

### 8.3 跟进：bootstrap 启动兜底被 early-return 跳过（生产实测发现）

**首轮上线后生产复核发现索引并未创建**：`pg_indexes` 中只有 `_pkey` / `_fk` / `_ifk` / `_uq`，无 `_suq`；且全量 93 次启动日志里只有「插件已加载，开始种子数据检查...」一行，**种子结果、drain、索引三条日志从未出现过任何一次**，也没有任何 warn。

- 根因：`bootstrap.ts` 的 `const defaultConfig = strapi.plugin("zhao-point").config("default"); if (!defaultConfig) return;`。Strapi 5 的 plugins loader 在 `applyUserConfig` 中执行 `plugin.config = defaultsDeep(plugin.config.default, userConfig)`（`@strapi/core/dist/loaders/plugins/index.js`），即把 `plugin.config` **覆写为已解包的 default 导出**，故 `config("default")` 恒为 `undefined` → 种子块当场 return，其后的 drain 与本次索引 DDL 一并被跳过（非报错，静默失效）。
- 修法（basic `87c7540b56`）：把两项**与种子配置无关**的启动兜底前移到种子块之前，并加注释说明该 early-return 的成因。**种子块行为保持不变**——不改 `config("default")` 的读取口径，因为改对会立即触发规则补种（对 `point_rules` 生产写入），属独立决策，另评估。
- 验收（生产实测）：
  - 启动日志出现 `[zhao-point] 到场记录唯一索引已就绪 (activity_attendances_signup_lnk_suq)`（`19:43:36`），首次出现在全部启动记录中。
  - `pg_indexes` 复核：`CREATE UNIQUE INDEX activity_attendances_signup_lnk_suq ON public.activity_attendances_signup_lnk USING btree (activity_signup_id)`。
  - 约束生效实证（事务内构造、事后 ROLLBACK）：同 signup 连插两条 → 第二条报 `duplicate key value violates unique constraint "activity_attendances_signup_lnk_suq"`；`ROLLBACK` 后 `count(*)` 复核为 **0**，生产无残留。
  - `/api/zhao-point/v1/activities` **200**，`strapi` online。

### 8.4 跟进：补齐到场记录及链路缺失的 DB 约束（2026-09-26）

对 `activity_attendances` 做了一次约束审计（`pg_indexes` + `pg_constraint` + `information_schema.columns`），确认还缺 5 项，全部已补（basic `9f33d77fe6`）：

| # | 对象 | 新增约束 | 缺失后果 |
|---|---|---|---|
| 1 | `activity_attendances.checkin_at` | `NOT NULL` | 到场记录可以没有到场时间 |
| 2 | `activity_attendances.geo_passed` / `points_granted` | `NOT NULL` + DB `DEFAULT true/false` | 布尔列三态化：签到幂等分支返回 `point: null`、台账按 `pointsGranted=true` 过滤会静默漏行 |
| 3 | `activity_attendances.method` | `CHECK (method IN ('worker_scan','self','manual'))` | Strapi enumeration 不建 CHECK，可写脏值 |
| 4 | `_lnk(activity_attendance_id)` | `UNIQUE`（`..._auq`） | schema 声明的 `oneToOne` 只做了一半：一条 attendance 可挂两条 signup |
| 5 | `activity_checkin_tickets.token` | `UNIQUE`（`..._suq`） | 一次性凭据的防重放底线缺失：token 重复时按 token `findOne` 命中不确定，`ticket_used` 单次语义可被绕过 |

**机制发现（决定全部走 bootstrap 幂等 DDL 的依据）：**
- `schema.json` 的 `required` / `unique` / `default` **只做应用层校验，均不落库**。实证：`activity-checkin-ticket.token` 声明了 `unique + required`，生产 DB 列仍**可空且无唯一索引**；`zhao_point_rules.action`、`zhao_website_geo_articles.article_no` 同理（都只有 pkey）。`@strapi/utils` 的 `getDoesAttributeRequireValidation` 也只把它们喂给校验。
- **列约束会被 schema sync 改回可空**：`@strapi/database/dist/schema/diff.js` 的 `diffColumns` **无条件**比较 `notNullable` / `defaultTo`，而目标 schema 里这两个值恒为 `false` / `null` → diff 判 CHANGED → sync 执行 `DROP NOT NULL` / 改默认值。故列级约束必须在 **sync 之后的 bootstrap 阶段**重新收紧（每轮启动重跑，运行期始终有效；实测跨两次重启 `is_nullable` 持续为 `NO`）。
- **索引与 CHECK 建好即稳定**：diff 的删除分支要求该对象**存在于 `previousTable`**（即曾被 Strapi 管理过），我们的索引/CHECK 不在其中，永不会被回收。

**实现**：`bootstrap.ts` 抽出通用 `ensureUniqueIndex(strapi, table, column, indexName)`（先按列查重，NULL 不参与比较，有重复只告警跳过）+ `ensureAttendanceColumnConstraints()`（逐列查空值再 `SET NOT NULL`，`SET DEFAULT`，`pg_constraint` 存在性守卫加 CHECK）。全部幂等、失败只 warn 不阻断启动。

**验收（生产实测）**：
- 启动日志逐条出现 5 项就绪；第二次重启时 `method 值域约束已创建` 不再出现（存在性守卫生效）。
- `information_schema`：三列 `is_nullable = NO` 且两个布尔列有 DB 默认值；`pg_constraint` 有 `activity_attendances_method_check`；`pg_indexes` 有 `..._auq` 与 `activity_checkin_tickets_token_suq`。
- 违例实测（事务内构造、事后 ROLLBACK，`count(*)` 复核三项均 **0**）：脏 `method` 被 CHECK 拒、缺 `checkin_at` 被 NOT NULL 拒、重复 token 被 `token_suq` 拒、同一 attendance 挂两条 signup 被 `auq` 拒。
- `/api/zhao-point/v1/activities` **200**。

**本次未做（已确认的剩余缺口）**：`token` 仍可空（UNIQUE 允许多个 NULL，写入侧恒有值，风险低）；`activity_signups` 无 `(activity, user)` 唯一（"同一用户同一活动至多一条报名"仍只在应用层事务保证，DB 层落地需给 `activity_signups` 加反范式列，成本高，需单独评估）；`_lnk` 两个 FK 列可空 → 允许 `(NULL, NULL)` 孤儿行；`lat`/`lng` 无范围 CHECK；`operator_id` 无 FK（指向用户或 admin 的裸 id，属设计取舍）。
