# 线下活动缺口盘点与补齐 — 设计

日期：2026-09-25
状态：已确认（用户批准批次划分与生产演练方式）

## 背景

线下活动模块（zhao-point + web 管理端 + shao C 端）功能面已完整，但生产 `activity_signups` / `activity_attendances` 均为 0 行，**全链路从未跑过真实数据**。近期将举办首场真实线下活动，0 数据风险在首场活动时集中爆发，因此以真实活动日期倒排优先级。

## 现状基线（已具备）

- 全生命周期：动态表单报名（候补/递补/取消/退费）→ 一次性票据签到核销（扫码/自助/手动+理由审计）→ 到场记录 → 积分扣/返、学习包授权
- 运营支撑：名单导出 CSV、统计看板、台账、评价、问卷门禁、SOP、分享裂变、咨询消息、日历、资源管理（场地/讲师/排期）、渠道权限三道门
- 硬化：5 处并发缺陷已修；报名 `(activity_id,user_id)` 部分唯一索引、到场 `_lnk` 唯一索引等 DB 兜底已上线生产实测
- 通知链路已存在：候补提醒、报名确认、开场前提醒（站内信即时 + 待办管理员手动发微信）、候补转正通知

## 缺口盘点

### A. 上线验证缺口（P0，真实活动前硬性）
1. **全链路 0 真实数据**：报名 → 候补 → 递补 → 取消 → 重新报名 → 三种签到方式（worker_scan/self/manual）→ 票据 5 分钟过期 → 积分扣/返 → 名单导出（已到场/未到场两种取值）
2. **并发 drill 未做**：双击报名、并发签到、并发取消+递补
3. **通知链路未实测**：站内信 + 微信四类通知

### B. 技术债挂账（影响真实活动，P0 随批次 1 一起清）
1. **bootstrap 种子块 bug**：`config("default")` 恒为 `undefined`，种子块 early-return，`point_rules` 补种被静默跳过——若生产规则缺失，真实活动积分会错
2. **`checkin_ticket.token` 可空**：UNIQUE 允许多 NULL，一次性凭据防重放底线留洞

### C. 技术债尾巴（P2，首场活动后清）
- `activity_attendances_signup_lnk` FK 列可空允许 `(NULL,NULL)` 孤儿行
- `lat`/`lng` 无范围 CHECK
- `operator_id` 无 FK
- `tests/permissions.test.ts` 21 例既有失败

### D. 产品功能观察项（P2，首场活动后按反馈定）
- 开场前微信提醒依赖「管理员手动发待办」，无自动定时——省轮询的既有取舍；首场若忘发会冷场，按首场反馈决定是否补

## 执行批次

### 批次 1（真实活动前，硬性）

**B1 修复 bootstrap 种子块**：将种子块/启动兜底逻辑中 `strapi.plugin("zhao-point").config("default")` 判空 early-return 移除或改用可靠判定（与种子无关的兜底必须放在任何 early-return 之前，见 bootstrap 启动兜底铁律）。验证：重启后日志出现种子检查结果、drain、索引三条日志。注意修对会立即触发 `point_rules` 补种——先核对生产 `point_rules` 现状再决定补种内容。

**B2 收紧 ticket.token NOT NULL**：幂等 DDL（bootstrap 内，sync 之后收紧），先查 NULL 违例，失败只 warn。验证：跨重启 `is_nullable` 持续 NO。

**A 生产演练**（B1/B2 部署后执行）：
- 建演练活动：标题带【演练】标记，报名窗口设为「现在起的 10 分钟」，活动开始时间设为约 30 分钟后；报名/候补/取消/递补演练完成后，管理端把活动时间改为过去时段再演练签到（避免报名期被时间校验拦截）；跑完即下架。C 端列表短暂可见可接受（用户已确认）
- 用测试账号（`admin`/`Admin@12345` + 真实 SSO 用户）跑全链路：报名 → 双击报名（验并发幂等）→ 候补 → 取消 → 递补 → 重新报名 → 三种签到方式 → 票据过期 → 积分扣/返核对 → 名单导出核对已到场/未到场/已取消三种取值 → 通知触达核对
- 演练数据不删（留作导出/统计样例），演练活动下架避免误报名

**验收标准**：全链路每步有生产实测记录（截图/DB 查询）；并发场景无重复报名/重复签到/重复递补；导出 CSV 各状态取值正确；积分账实相符；四类通知至少站内信全部触达。

## 风险点

1. **B1 修复触发补种**：修对 `config("default")` 判定后，种子检查会真正执行——若生产 `point_rules` 已被人工改过，补种可能覆盖/新增规则。**先查生产现状，再决定是否需要调整种子内容**。
2. **演练污染 C 端**：演练活动短暂可见（已接受）；活动时间设为过去时段可避免 C 端误报名，但仍需在下架前观察。
3. **测试账号积分污染**：演练产生的积分进出挂在测试账号上，验收后需核对不留影响真实用户的残留。
4. **dist 部署铁律**：B1/B2 改 `server/src` 后必须本地 `npm run build` 重建 dist 一并提交，部署后 Grep dist 验证关键字。
