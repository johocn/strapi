# SSO sso_users 主键序列失步自愈设计 20260913

## 背景

商品详情页微信分享给好友 → 好友点击登录 → 统一登录页（h.joho.cn）微信授权回调创建新用户时中断：

```
insert into "public"."sso_users" (...) values (...) returning "id"
- duplicate key value violates unique constraint "sso_users_pkey"
```

## 根因

`sso_users.id` 为自增主键，其序列 `sso_users_id_seq` 的 `last_value` 落后于表内实际 `max(id)`：

- **数据库备份恢复**（pg_dump / pg_restore）默认只恢复数据与序列当前值，不自动 `setval` 到 `max(id)`；
- **显式 ID 合并**（历史数据/多环境合并时直接带 id 插入）同样会造成序列落后。

此后 `nextval` 返回的 id 落在已占用区间，新用户 `INSERT ... RETURNING id` 即报主键冲突。该故障在备份恢复后**首个新用户注册/微信登录**时必然触发，且仅出现一次（序列推进越过 max 后自愈），难以复现、极具隐蔽性。

## 方案：代码自愈 + 启动自检（方案 B）

### 1. `sso-user` 服务新增两个方法

- **`syncSequence()`**：幂等同步序列。
  - 读 `sso_users_id_seq.last_value/is_called` 与 `sso_users.max(id)`；
  - 计算 `next = is_called ? last_value + 1 : last_value`；
  - **仅当 `next <= max(id)`**（即将撞上已有 id）时才 `setval(max(id))`，正常时零开销；
  - 自身 try/catch，失败仅告警不阻断业务。

- **`createSsoUserWithSeqGuard(data)`**：创建守卫。
  - 正常走 `db.query(USER_UID).create({ data })`；
  - 捕获 PG 主键冲突（`23505` / `duplicate key` / `sso_users_pkey`）→ 日志告警 → `syncSequence()` → **重试一次**；
  - 非主键冲突原样上抛。

### 2. 三处用户创建路径全部接入守卫

| 路径 | 位置 | 说明 |
|---|---|---|
| 密码/短信注册 | `sso-user.createUser` | 常规注册入口 |
| 微信登录新用户 | `sso-wechat.handleCallback` | 本次故障现场 |
| 虚拟用户兜底 | `sso-invite.getOrCreateVirtualUser` | 邀请码 creator 缺失时的兜底建号 |

### 3. `bootstrap.ts` 启动自检

插件启动时调用 `syncSequence()`，备份恢复后重启服务即自动纠正序列，从根上消除故障窗口。

## 代码要点

- 冲突判定 `isPkeyViolation`：`msg.includes("sso_users_pkey") || msg.includes("duplicate key") || e.code === "23505"`；
- 幂等：正常态 `nextval > max(id)` 不触发任何写操作；
- 兜底链完整：守卫失败告警 → 重试 → 仍失败则正常抛错（不会吞错导致静默失败）。

## 部署要点

- zhao-sso 改源码必须本地重建 dist 并随 git 提交（插件 dist 部署铁律）；
- 部署：`node scripts/deploy.mjs`（本地构建 → scp 产物 → 服务器解压）→ pm2 restart；
- 启动自检无需任何环境变量，默认开启。

## 验收

1. **启动自检**：部署重启后服务正常，日志无错误（正常态幂等，无输出）；
2. **模拟失步自愈**：将序列 `setval` 到小于 `max(id)` → 触发一次创建（微信登录/注册）→ 日志出现「主键冲突(序列失步)，同步后重试」→ 创建成功；
3. **清理**：回归验证产生的测试用户删除，序列恢复自然推进。
